# 決定記録の共通運用

ChatGPT・Claude Code 共通。GitHub `main` の承認済み仕様・決定・契約が正本。会話、Draft PR、Issue、Drive の記録は正式反映前の証跡であり、未統合の決定を実装許可とみなさない。

## 参照先と適用範囲

| ファイル | 内容 |
|---|---|
| [adopted-decisions.md](adopted-decisions.md) | 採用済み決定、置換・廃止の履歴、旧 ID 対応表。移行前の DEC-001〜048 は主要決定の抜粋であり、旧 Drive の全履歴は移行前記録として保管する |
| [../spec/](../spec/) | ゲーム仕様 |
| [../contracts/](../contracts/) | 実装契約 |
| [../spec/pending-approvals.md](../spec/pending-approvals.md) | 未承認事項 |
| 関連する領域資料・Issue・PR | 検討中の構想、実装計画、進捗、検証証跡 |

着手時に main と関連する未統合 PR を確認する。関係する決定だけを参照し、全資料の毎回読込は不要。正式反映済みの方針は再承認しない。既存方針だけで決まる内容と、ユーザー判断が必要な新規論点を区別する。

## 意思決定の扱い

- 採用・不採用・支持／検討中・保留を区別する。明示採用には定型的な承認文言を要求しない。上位方針の採用を未承認の勝利条件、GAME-01〜05、具体ルール、実装方式に拡大しない。
- 採用済みの重要な決定は、決定本文、理由、採用根拠（会話の日付・参照先・対象となった案またはユーザーの発言）、適用範囲、未決事項、置換対象を記録する。採用と実装可否・実装完了を区別する。
- 支持・検討中・保留の構想は既存の領域資料や関連 Issue に記録し、DEC として確定させない。個々の進捗を決定台帳やルート指示に複製しない。
- main に存在する ID は永久に予約済みとし、欠番を再利用しない。変更・廃止しても旧決定を削除せず、変更理由・後継決定を残す。

## 共通受付と採番

新規 DEC の発行、および台帳の追記・修正は同一リポジトリ内の固定ブランチ **`docs/decisions-inbox`** から main への共通 PR に集約する。各会話・実装 PR で独自の番号を発行しない。実装 PR では正式な DEC を参照し、必要な新規決定は受付へ渡す。

1. main の HEAD、受付ブランチの HEAD、同ブランチの open PR、その他の関連する未統合決定を照合する。既存の受付 PR があるなら別の受付 PR を作らない。
2. 受付に既に同じ採用根拠・同じ内容の記録がないか確認する。必要なら main と受付の最新台帳、関連する移行中の PR で確認された予約済み番号の最大値を超える ID を採番する。
3. 最新受付 HEAD を親としたコミットを作り、**非 force の fast-forward かつ期待 HEAD の一致を確認した更新**を行う。並行変更で拒否されたら取得し直し、重複・差分を確認して再採番する。ブランチの初回作成も既存 ref を上書きせず、作成競合時は再取得する。ID の発行成功は commit と ref の読戻しで確認する。更新未確認の番号を確定として報告しない。
4. 新規受付 PR は下書きとして開始してよいが、記録の確認ができた時点で速やかに Ready for review とする。レビュー対象の HEAD を固定し、新規案件は別番号を先行発行せず、関連 Issue または受付 PR コメントに採用根拠と未採番であることを記録する。追加編集が必要なら対象 HEAD・レビュー・CI・統合承認を確認し直す。
5. 受付 PR の統合後は main に反映された内容を読み戻す。固定ブランチが残る場合、前回統合済みの HEAD と現在 HEAD が一致し、未反映記録がないことを確認する。最新 main と旧受付 HEAD を親にした、内容が最新 main と同一の fast-forward 更新で次の受付を開始してよい。未反映の変更や閉じただけの PR があれば消さず、先に調整する。force push、未確認ブランチの削除、別セッションの作業の上書きはしない。

## レビュー・統合

議論の区切りや重要な採用直後に未記録・未統合の決定を確認し、採用済みの決定だけを長期間 Draft PR に蓄積しない。記録済みのものは個別の実装完了を待たずにレビュー・統合承認へ進める。

- 差分の内容、採用根拠、適用範囲、未承認事項との境界、main の既存定義、他の PR との重複を確認する。未統合の旧 ID を振り直す場合は出典 PR・旧 ID・統合 ID・内容の対応表を残し、影響する参照先を修正する。公開済み ID は振り直さない。
- 必須 CI の `quick-check` が成功し、対象 HEAD、最新 main との整合性、必要なレビューが確認できたら、統合する PR・範囲を明示してユーザーに承認を求める。採用済みの内容そのものを再承認させない。
- 明示承認後のみ、確認済み HEAD を指定して Squash merge。main の読戻し後、統合済みになった旧 PR を整理し、必要な実装 Issue へ参照をつなぐ。旧 PR に未統合の変更が残る場合は閉じない。無関係な実装作業は先行可能。
- main に反映されるまでは「記録済み・未統合」と報告する。GitHub が参照・更新できない場合は未確認範囲を明記し、推測で採番・承認・統合をしない。

## 機械検査

`scripts/check_decision_records.py` を既存の必須 CI `quick-check` の一部として実行する。標準ライブラリのみを用い、旧形式の複数 ID 行も検査する。main への台帳変更元、ID 重複・不正な形式・欠番再利用・既存 ID の消失、旧 ID 対応表の重複・参照先・変更／消失を検出する。既存定義の本文変更はログに示す。意味上の妥当性、採用根拠、領域文書内の参照の完全性、未統合 PR 間の衝突はレビューで確認し、CI 成功を代用しない。

```sh
python3 -I scripts/check_decision_records.py --self-test
python3 -I scripts/check_decision_records.py
```

初回導入時は既存の決定統合 PR #146 のレビュー・承認・統合を先に行い、旧 PR 由来の決定を取りこぼさないことを確認してから、本運用と CI を有効にする。以後は固定受付経路を使用する。
