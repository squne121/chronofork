# ゲーム体験・UI/UXの検証と改善サイクル（提案）

**状態:** 2026-11-13に検討用として作成。ユーザーによる具体運用の採否確認とPR統合までは正式採用済みではない。  
**適用範囲:** Chronoforkのプレイテスト、情報設計、UI操作性、ゲーム体験の評価。シミュレーション・ゲームバランスの評価との接点を扱うが、ゲーム規則や仕様を変更しない。  
**正本との関係:** 体験目標は `docs/spec/mvp-spec.md` と `docs/decisions/`、未確定のUI構想は `docs/design/experience-and-ui-ideas.md`。個別タスクの進捗・証跡は既存Issue/PR。本書は評価の**方法**のみを扱い、構想の採否や実装計画を代替しない。

## 1. 目的と基本原則

- 「人間が試す→違和感を伝える→修正する」を、**狙う体験→検証可能な仮説→観察→原因の切り分け→最小変更→再検証→学びの記録**という反復にする。
- 体験上の問題と技術的不具合、表示の問題とシミュレーション上の結果を分ける。感想は重要な観察だが、感想に含まれる原因説明を無検証で確定しない。
- 変更前後の確認条件を揃えられる場合は、同じ実装構成・seed・歴史枝・観測年・介入条件等を使う。条件が異なる比較は区別する。
- **操作可能**、**意味を理解できる**、**自分で調べ・介入したくなる**を別の評価対象とする。ユニットテストやCIの成功だけで人間のUX成功・面白さを宣言しない。
- クリック数や所要時間は必要な場面だけ補助指標として用い、短いこと自体を目的にしない。ゲームとして意図した思考や探索の難しさを、UIの分かりにくさと混同しない。
- MVP第1縦断のプレイアブル化を優先し、毎回の小修正に大規模な調査・評価手続きを義務付けない。

## 2. 作業ごとの最小の検証ループ

1. **対象体験を決める。** 既存の承認済み体験目標から、今回の改修で変えたいプレイヤー行動・理解・印象を一つか少数選ぶ。未承認の価値判断は「仮説」と明記する。
2. **反証可能な仮説を置く。** 「誰が、どの状況で、何を理解・実行できるはずか」「実際にそうならなければ何が否定されるか」を簡潔に定める。原因候補は複数を許容する。
3. **検証方法を選ぶ。** 不具合・正本性は自動テストやAIのブラウザ操作、情報理解は行動観察と非誘導の質問、興味・手応えは人間の自由試遊を中心にする。全手法を毎回実行する必要はない。
4. **観察と解釈を分ける。** 何が起きたか、本人が何と言ったか、AI/開発者の原因仮説、証拠、未確認事項を別扱いにする。AIが「初心者を演じた」結果は人間の初見体験の実証にしない。
5. **最小変更と比較を行う。** 既存仕様と実データへの忠実性を保ち、必要な範囲の実装・テストを行う。修正で何が改善したと判断でき、何が未確認かを報告する。
6. **学びを残し次を決める。** 仮説が支持・否定・未確定のいずれか、再利用できる知見、次に確認する点、今回の改修を閉じるかを記録する。

## 3. 人間とAIの役割分担

| 手段 | 主な役割 | 判定してはいけないこと |
| --- | --- | --- |
| Vitest・Playwright・実Worker/ブラウザ試験 | 機能成立、UI操作、回帰、性能、実データとの一致 | プレイヤーが理解した・面白いと感じた |
| AIによる画面点検・探索 | 操作の行き止まり、視認・配置・名称・導線の問題候補、想定外の操作経路の発見 | 人間の理解・好奇心・継続意欲の代替評価 |
| AIによる分析 | 行動・発言・実ログ・スクリーンショットを分離し、競合する原因仮説と最小検証を提案 | 根拠のない因果断定、本人の意思決定の代行 |
| 人間の自由試遊 | 自然に生まれる疑問、探索、自発的介入、比較後の次の仮説や継続意欲を観察 | 単一例から全プレイヤーの傾向を一般化すること |
| 人間の課題型試遊 | 指定された情報に自力で到達できるか、どこで支援を要したかを確認 | 指定された課題の達成を自発性の証拠にすること |

- 初見の情報探索をAIで検査する場合、画面から読み取る担当には内部の正解手順・実装コードを先に与えない。世界・因果の正確性を検査する別担当は `WorldState` / `EventLog` / `DecisionTrace` を参照してよい。
- 本人試遊は重要だが、開発背景を知ることによる慣れがある。初見理解や広いプレイヤー層への適合を判断する段階では、外部プレイヤーによる少人数の探索的試遊を別途検討する（現MVPの必須条件には追加しない）。

## 4. 評価の対象と切り分け

少なくとも必要に応じて以下を区別する。

- **操作・表示:** 年/枝/対象の現在地、入力への応答、名称と概念の区別、視認性、キーボード操作、表示幅、誤解を招く状態表示。
- **情報理解:** 年表→人物/Title→判断根拠の関係を理解できるか。未記録・未確認・確定を区別できるか。情報に到達することと意味を理解することを別に観察。
- **探索・ゲーム体験:** 本人が自分の疑問を持ち、介入の予想と理由を作り、結果から新しい疑問や試行を考えるか。正解・勝利の達成のみを合格条件にしない。
- **シミュレーションの実効性:** 介入によって変わった入力値、判断の採否、Event、状態、技術Goalを実ログで照合する。表示で差分が見えない場合と、実際に差分がほぼない場合を分ける。「変化なし」も真実として見せ、必要なら試験用パラメータの感度を別に調査する。

## 5. 知見の蓄積と一区切りの判断

個別Issue/PRへ、**対象ビルド・条件、観察、原因仮説、修正/比較、検証結果、再利用可能な学び、残る不確実性**を短く関連付ける。既存のコメント・テスト・スクリーンショット・ログを参照し、同じ情報の専用台帳を増やさない。知見が複数の画面や後続開発にも通用すると検証された場合のみ、関連する設計資料の最も狭い場所へ要約する。

改修の終了・継続は、単なる新しい不満の有無ではなく、当初の対象体験と技術品質の達成、残問題の重大度、改修コスト、MVP完成への寄与で判断する。評価対象が成立したら、その範囲の改修は閉じ、追加の魅力案は別の検証課題へ分ける。操作と理解が成立しているのに体験が弱い場合は、UI変更を延々と続けず、実歴史の変化量・介入の実効性・ゲーム規則の問題がないか切り分ける。

正式Goal・シミュレーション規則・世界設定・未承認GAME-01〜05・ライセンス・新たな情報公開方針は、この方法論から自動的に変更しない。重要な変更はユーザーの判断と既存の正式記録手続きを要する。
